## Critical findings / exact counterexamples

C1. **Legacy manifest/CSV/per-agent rejection contract is missing.** Kernel normalizeSubmission (68-74) accepts only normalized identity+orders; it never requires/parses the original manifest or orders.csv. An identity-correct object with orders:[] and NO manifest is accepted as valid_hold, whereas v3.2 rejects missing manifest even for hold. settleRound (86-94) throws the ENTIRE round for either invalid/infeasible agent; v3.2 records that agent's all-or-nothing failure and independently settles the valid other agent. For any valid two-step round, agent-one orders [{decision_close:D,side:'buy',quantity:1},{decision_close:D+dt,side:'buy',quantity:1000}] at prices100/C1000 and valid agent-two buy1 cause candidate insufficient_cash/no returned settlement; legacy rejects all agent-one orders but applies agent-two's buy. Input-copy nonmutation is good but does not prove preserved per-submission settlement/failure evidence. A deliberately stricter run-abort policy must be explicit, durable and reconciled with legacy, not called equivalence.

C2. **Timestamp scheduling changes the strategy/fill protocol.** Candidate allows one order at EACH decision close inside a round; legacy accepts an ordered file of arbitrary multiple rows, ALL filled at the one next close after the round's initial decision. With B=3, candidate accepts {decision_close:D+2dt,side:'buy',quantity:1} and fills D+3dt; actual v3.2's round order fills D+dt. Candidate rejects duplicate decision timestamps/over B rows even when those legacy file-order trades are feasible. Retain the legacy single-decision/multiple-order protocol or obtain explicit protocol-change acceptance; do not silently claim regression equivalence. Candidate's strict [round_start,round_end) bounds and +dt fills are internally sensible for its DIFFERENT protocol. Its final allowed fill is at evaluation_end, not end+dt.

C3. **No durable private/recovery adapter exists yet.** Kernel create/prepare/settle return full mutable state values; there is no authoritative storage, per-run serialization, accepted-submission freeze, cached-settlement lookup, commit/publication protocol or replay recovery. Given returned post-settlement state s1, settleRound(s1,original_submissions) throws round_not_awaiting_submissions instead of returning the committed round's view.
